# Prefill 复核：对齐输入长度后是否变慢

2026-10-03。上次快速基准新增约 1K 输入并省略约 16K 输入，没有把新旧场景对齐展示，容易造成“从一千多降到六百”的误解。实际约 1K 和约 4K/16K 输入的吞吐不可直接比较。

同条件对照显示约 4K/16K 的 prefill 提升约 3%，没有从 1000+ 降到 600 的退化。输入较长时，固定调度和数据准备开销更容易被摊薄，批量计算的利用率也可能不同；每秒 token 数较高，并不意味着整个请求等待更短。

| --- | ---: | ---: |
| 约 4K 输入 prefill | 1432.2 | 1457.3 |

单位 tokens/s；三次中位数。此表仅用于辨认历史测试口径，不能作为严格优化 A/B：历史是原版，当前是 SC117；输入约 3877–3882 / 15459–15460 tokens，而此次为 3842 / 15423 tokens；历史输出上限 256，此次 128。16K 用例沿用旧验收脚本生成资料的方式和首轮口令，system 不再加随机 UUID。

最早原版约 4K 的三次 prefill 为 1011.6 / 1438.9 / 1432.2；约 16K 为 1921.7 / 2223.0 / 2245.3。首轮较慢，专家缓存及预热状态会影响数字。所有历史及本次比较请求 cache_n 均为零。

## 后续基准约定

- 默认一键快测保持原来的短输入、约 1K、约 4K 三档，约 22 秒，不改变已固定的基准输入。
- 比较历史 2000+ prefill 时额外运行约 16K 档，并标明模型与输出长度；不能拿约 1K 档直接比较。
- 每次同时报告实际输入 tokens、prefill、decode 和首字等待；把热服务快测与重启后的测量分开。
- 两组及热服务复测总共 48 个请求通过检查；每个正式请求都输出 128 tokens，cache_n=0。
- 测试结束恢复已选定配置；上下文仍是 32K，fused 开启、视觉按需加载，服务未启用开机自启。
