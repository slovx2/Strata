# Song PC Strata 性能剖析（2026-10-04）

本轮测试的是 SC117 IQ3_S 原生引擎：RTX 4080 16GB、i5-13600KF、WSL 56GB 内存上限、INT8 KV、MTP 开启。测试上下文容量 32768，输入占用 256/4096/16384 token。正式配置仍为 256K；本报告不能外推为 256K 已占满时的性能。

## 主要结论

1. **Decode 优先处理专家供给等待。** GPU 等待专家到位的时间明显大于暴露出来的 CPU 结果等待。说明应优先平衡“CPU 就地计算”和“搬到 GPU 计算”，不能简单地认为交给 GPU 越多越快。这不是已证明 PCIe 物理带宽饱和；等待还包括 staging、同步和调度。
2. **Prefill 优先处理拷贝与计算的重叠。** 4K 输入的 GPU 时间线约有一半是 `wait copy`；16K 输入降至约三分之一。纯矩阵计算并不是当前唯一主导项。
3. **找到了低复杂度的候选优化。** 不增加 GPU 计时探针时，第一轮相邻、显存命中率接近的对照中，把 `pcie_frac` 从 0.55 调至 0.25，三个领域 decode 提升约 27%–37%。第二轮有明显暖缓存影响，不能把全部增益都算成参数收益。尚未应用到正式配置。
4. **多样输入确实触发了专家缺失和搬运。** 同一无 GPU 探针对照中显存命中率约 42%–86%，不是全部专家都在显存里的理想情况。RAM 常驻专家模式下，各推理请求的专家文件读取计数均为零，未发现专家从 SSD 逐请求加载是主要瓶颈的证据。

## 测量范围与结果

共 88 个独立合成请求（含预热），前缀缓存关闭，输出上限 192 token。涉及 Go、网络诊断、中文小说、数学、英文科学、多语言结构化数据。不读取真实对话；不记录生成正文、推理文本、工具参数、输出 token ID 或内容哈希。没有图片与长对话测量。

计时包含原生引擎 prefill/decode，不包含 HTTP、网络与分词时间。正常吞吐以未开启 GPU 探针的数据为准；细分计时用来定位等待。每项两轮，缓存会自适应，MTP 接受率和实际生成路径也会变化；这不是固定路由/固定输出 token 的微基准，也没有质量等价性验收。

### 关闭 GPU 探针后的搬运比例对照

`pcie_frac` 是对显存未命中专家的 GPU 分担目标比例，0 仍使用显存内已有专家。只启用原生已在累计的 host counters 输出，不增加 GPU timestamp kernels。每个输入按正序、倒序分别测一轮，以降低单向暖缓存偏差。

| 4K 输入 | 0（CPU处理缺失） | 0.25 | 默认0.55 | 0.25相对0.55 |
|---|---|---|---|---|
| 网络诊断 | 55.9 | 60.6 | 37.2 | +62.9% |
| Go 代码 | 49.4 | 59.2 | 41.8 | +41.6% |
| 中文写作 | 49.0 | 61.1 | 41.1 | +48.8% |

## Prefill 与资源情况

4K 请求的 GPU 时间线为 2.43–2.68 秒，其中等待拷贝约 1.17–1.19 秒（约 44%–49%）。热身充分的请求多为 2.43–2.45 秒，等待占比约 48%。例如 Go 请求中，融合专家 GEMM 约 413ms，GDN 的投影/卷积/递推/输出约 385ms，QSA 约 184ms。它们是插桩后的阶段经过时间。

16K 输入的 GPU 时间线约 6.63–6.73 秒，等待拷贝约 2.17 秒（约 32%–33%）；输入批次扩大后更容易摊薄等待。256-token 短输入则受分组、启动等固定成本影响，所以 prefill tok/s 明显更低，不能与 4K/16K 直接对比。

当前配置约 8.09GiB 显存用于专家缓存，约 41.74GiB RAM 常驻其余专家。主测试采样中可用内存最低约 7.92GiB，最高 GPU 温度 62°C，最高功耗约 235W；这些读数不足以证明频率、功耗上限或温度是瓶颈。主测试请求区间内系统换入约 10MiB、换出约 60KiB，未见大规模交换风暴。计数是整个 WSL 的，不是精确进程归因。专家 `file_blobs/file_mb=0` 不等于整个系统零磁盘访问。

## 下一步优化优先级

| 优先级 | 方向 | 复杂度与收益判断 |
|---|---|---|
| 1 | 验证 `pcie_frac=0.25` 的 CPU/GPU 分工 | 改参数成本低；已有跨三类输入的正向证据。下一轮用更多独立重复、交换顺序，再验证正式 256K 配置与输出质量。 |
| 2 | 专家缓存驻留与领域切换 | 命中率波动明显；先测现有缓存策略与预热/持久化功能，不急于重写。更大显存可能减少缺失，但本次不能估算换卡收益。 |
| 3 | Prefill 的 staging、拷贝重叠与分块 | 有约 48% 暴露等待，但不能认为全部可消除。应先尝试已有分块/队列参数，再决定是否值得修改流水线。 |
| 4 | 单个注意力或 GEMM 内核微调 | 目前优先级较低；先减少专家供给等待，再依据新的 profile 判断计算内核是否成为主瓶颈。 |

若要再区分“实际 DMA 慢”“CPU 发起搬运晚”“缓冲区/依赖同步卡住”，下一步需短时采集 CPU、CUDA stream 与 memcpy 的关联时间线。本轮已有探针足以发现等待方向，但无法完成这三个原因的最终归因。

## 统计口径修正

发现原生 `hits/lookups` 的分母只包括显存命中项和 CPU 未命中项，漏掉了 PCIe 分支。它可能显示接近 99%，而实际显存命中约 73%。本报告将分母改为 `(草稿提出数 + 验证窗口数) × 48层 × 10路由专家`。未记录窗口数的基准提供末窗口截断造成的上下界估计，原始比值仅保留用于审计。当前没有修改或重新编译生产推理内核。

Prefill 日志的 `host staging` 是跨请求累计值；解析器先作差再显示。主线程 staging 与 GPU 活动重叠，不能相加。

## 如何阅读附件

- `Song-PC-Strata-性能剖析.html`：离线交互报告，可切换每个请求查看 prefill 阶段、decode 等待和 GDN/QSA 分类。
- `results.json`：原始数字结果；`parsed.json`：修正口径后的结构化数据。
- `resources.jsonl`、引擎日志：资源采样与原始计时；补充无 GPU 探针对照在 validation 子目录。
- `tools/`：复现、解析、报告生成脚本及计数回归测试。

本次按 GDN/QSA 类型汇总，没有逐 layer ID 排名，没有 Nsight 全线程/全 stream 时间线。`wait copy`/`waitB` 是暴露在执行路径上的等待，已经被计算掩盖的 DMA 时间不在其中。GPU 利用率会把等待内核计入忙碌，不能据此断言算力已用满。

正式配置保持原样，测试原生子进程结束；服务保持开始前的停止状态，开机自启未改变。
