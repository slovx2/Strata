本轮结论：以已合入主干 0.1.39 的版本作为稳定基线，本轮新候选暂不作为正式默认优化。确实有微基准收益，但充分预热、交叉顺序复测后，正式负载收益不足以与波动区分。最有潜力的是弹性 KV 原型，保留研究结果，尚不能直接兼容现有图片功能。

## 如何测试

- 设备：RTX 4080 16GB、i5-13600KF、WSL 内存上限 56GB。本轮未修改 Windows/WSL 内存配置。
- 模型：SC117 IQ3_S；MTP 开启；INT8 KV；`pcie_frac=0.25` 全程固定。
- 基线：`5bf523a9c0a5dfaf1cb14eaa3d4924c3f33cdf50`，已包含主干 0.1.39。不是早期 0.1.36，也不能直接与以前单一网络场景的 58.7 token/s 比。
- 每个候选从同一基线独立修改、独立启动。初筛后，对可能有效的组合及最简单的单项进行交叉顺序复测。
- 网络、Go、中文叙事、数学、科学和多语言结构化材料，全部为合成输入；独立请求，不做连续对话和并发测试。
- 共 560 次测量请求，另有预热和诊断采样。通常输出 192 token；短 prefill 专项为 64，固定路径正确性为 128。
- 常规容量 32K；弹性 KV 及最终正式配置对照为 256K。**256K 是配置容量，实际最长测试输入为 32,768 token；没有宣称完成满 256K 输入的性能/质量验证。**
- 不保存用户聊天、生成正文、token ID、专家 ID 或内容哈希。正确性对照只保存相等/不相等的布尔值。

## 正式配置下的最终对照

256K、正常图片显存借用、MTP、INT8 KV；A/B/B/A 顺序，每组重启引擎并预热全部输入。A 为默认搬运 kernel 的 384 个 blocks，B 只改为 96。

| 指标 | 基线 384 | 仅改 fetch96 | 变化 |
|---|---:|---:|---:|
| Prefill token/s | 1455.80 | 1456.89 | +0.07% |
| Decode token/s | 41.09 | 41.55 | +1.12% |
| 平均首 token 时间 | 2.508 秒 | 2.492 秒 | -0.65% |
| 平均请求总耗时 | 7.116 秒 | 7.063 秒 | -0.74% |

四次独立启动的 decode 分别为 40.44、40.49、42.66、41.75 token/s。改动收益比启动间波动小，因此不能认定稳定加速。**正式默认仍为 384，96 仅保留为可选实验开关。**

B2 测量期间，系统 Linux 换页计数增加 99,710 页，约 389.5MiB；其他三组为零。它是系统级计数，不能直接认定由 Strata 引起，也不能忽略为“内存完全充足”。本轮没有据此修改内存配置。

## 为什么没有把微基准的加速算作模型加速

fetch 微基准测试同一个搬运 kernel，从固定页内存读取轮换的数据块：16 个 2MiB 块，384 blocks 约 2.874–2.887ms，96 blocks 约 1.927–2.181ms，字节校验全部通过。

但请求总耗时还包含其他 GPU 计算、CPU 专家、MTP 草稿及验证、同步、prefill 和调度。一个搬运 kernel 变快，并不保证它在真实执行时仍然占相同耗时，也不保证其他工作不会成为瓶颈。因此最后看完整请求，而不是只看这个 kernel。

32K 的组合复测采用 A/B/C/C/B/A，每次加载后全量预热：

| 组合 | Prefill token/s | Decode token/s | 平均请求耗时 |
|---|---:|---:|---:|
| A 基线 | 1594.34 | 50.84 | 6.005 秒 |
| B fetch96 + 搬运独立流 | 1573.98 | 51.17 | 6.018 秒 |
| C B + THP + 准入门槛 3 | 1573.27 | 51.88 | 5.959 秒 |

C 两次加载为 244.9/246.9 秒，A 为 197.0/212.4 秒。这不是严格冷启动实验，但当前收益不足以支持引入这组复杂改动。

## 弹性 KV 为什么值得保留研究

固定分配 256K 的 KV 容量，即使请求只有几千 token，也会占据对应显存。按需增长把暂时不用的 KV 显存交给专家缓存：这个原型的初始专家槽位从 2471 增到 4107，约 +66%。命中更多常驻专家，可以减少部分 CPU 计算或专家读取需求。

这次原型的 decode 为 42.64 → 48.38 token/s，平均请求 9.415 → 8.845 秒。测试覆盖 KV 增长至 40960、缩回 8192，以及 163 个专家槽位的交还/回填。它不是未经修改直接合入的社区 PR。

限制是：两组都临时关闭图片借用进行文本隔离测试；原型允许缺失专家回退到 GGUF 读取，累计专家文件读取 41.5MB。系统数据盘读取也由 91.5MiB 增至 1169.2MiB，但不能把系统全部 I/O 都归给 Strata。要进入正式服务，需要把 KV 增缩、专家缓存、图片借用的显存所有权和失败恢复统一起来。

## 正确性与测量边界

- 固定 CPU/GPU 执行路径和缓存布局、关闭动态换入后，搬运/重叠/THP 实验组合对 14 个输出序列全部与基线逐 token 相同；同组重复也全部一致。只保存比较布尔值。这支持该固定条件下的正确性，不是全面质量证明。
- 正常自动调度下，基线自身跨请求也不总是逐 token 一致。CPU/GPU 舍入、缓存轨迹及推测解码策略都可能影响序列，不能把一般对照中的不同输出直接判成权重损坏。
- 多数候选通过 69 项原生测试；弹性 KV 原型通过 70 项。基线固定排除两项：缺测试资产的 `ple_parity`、不适合当前指令集的 `expert_multi_test`，不把排除算作通过。
- Decode 采用“所有生成 token 数 / 原生 decode 时间”。此前临时脚本减去首 token 的做法已纠正，因为引擎计时包含首个输出；原始耗时没有改写。
- CPU/GPU/PCIe 专家路由比例统计的是专家分派数量，不是 FLOPs、执行时间或硬件利用率。`pcie_frac=0.25` 更不等于 GPU 有 25% 时间在等待。
- 多流诊断与性能跑分分开；插桩本身会扰动执行。详细原始数值、补丁及来源 revision 随实验归档提供。


## 搬运与等待诊断补充

使用同一份带插桩的实验二进制，分别设置默认384与96，其余实验开关关闭；保留主干已有的共享专家重叠。两组各采样18个窗口，来自网络、数学、中文叙事的6次测量请求。它们不是正式跑分二进制，不能用这些耗时取代前面的性能对照。

| 采样窗口的中位数 | 默认384 | fetch96 |
|---|---:|---:|
| 整个窗口 |37.57ms|39.06ms|
| 已记录的 GPU 计算区间并集 |14.93ms|14.95ms|
| 专家搬运区间并集 |7.03ms|5.87ms|
| 扣除其他已记录 GPU 活动后，暴露的 verify 等待 |4.16ms|5.66ms|

这次抽样也支持“搬运 kernel 变快，但请求未相应变快”。不过采样有限，不能当成因果证明。

还必须说明一个异常长窗口：fetch96 中一次窗口为424.37ms，其中第一层等待 CPU 结果的 GPU 区间为389.73ms，而对应已记录 CPU 专家计算区间只有0.86ms。不能把389.73ms解释为 CPU 算了这么久，也不能认定是专家复制。现有记录尚不足以分清同步、运行时调度与插桩影响；本轮保留样本，没有臆测根因。

如果直接对这18个窗口求和，“暴露等待/窗口时间”会得到基线11.42%、fetch96为44.35%，后者被上述长尾强烈影响。它们只描述这份采样；草稿等 GPU 工作没有完整覆盖，**不是整段请求的真实 GPU 空闲率**。表内各项是分别取的中位数，不能相加成总时间。

缓存换入的另一组阶段计时，包含预热，共159个换入批次：

| 每批次平均阶段耗时 | 默认384 | fetch96 | 含义 |
|---|---:|---:|---|
| 备份被替换专家 |5.07ms|5.40ms|保存仅在 GPU 上的旧专家，包含回传等待和管理工作 |
| 等待新专家换入 |7.62ms|7.72ms|发布前等待异步换入完成；不是复制的完整总时长 |
| 更新 RAM 专家存储 |6.81ms|8.72ms|完成 RAM 中的专家交换/数据复制 |
| 更新驻留映射 |0.079ms|0.088ms|把新的槽位映射发布给 GPU |

两组统计的换入数量相同，但阶段可能与其他工作重叠，不能相加成请求关键路径。后续更值得针对“换出回传、RAM 二次复制、结果发布的长尾”做定位；单纯减少 fetch 的 blocks 并没有解决这些成本。旧 timeline 网页没有替换成此实验数据，避免混用不同时间戳格式。
