## 合并处理

- 保留工具调用恢复、受限的 reasoning EOS 续写和结构化脱敏日志；使用上游最新服务逻辑，包括 Responses、字面 think 标签处理和失去响应时的处理。
- 保留单卡 CPU prefill assist，以及短提示词 staged 路径的批量 gather。stream-all 路径采用上游的新分组 gather、环形缓冲区归还规则和按字节配置的 prefill ring。
- 保留按需图像编码器的 LEND/RECLAIM。它和上游 `--vram-elastic` 是两套 VRAM 管理实现，明确互斥，不允许两个管理器同时控制同一片内存；LEND 也不与并发 batch 混用。
- 保留 target-only（不加载 MTP）的已有路径；本次真实模型回归使用目前的 SC117 + MTP 配置。
- 旧的三文件增量诊断构建增加兼容性检查：基础库对应的代码不一致时拒绝复用，要求完整 CMake 编译。

## 根据新代码，接下来如何减少搬运与等待

以下是本机的待验证建议，不是已经测出的收益。

**先把等待拆准。** 旧图中部分窗口的 prepare 为 12.97–14.64 ms，包含 `apply_pending` 等多项工作。
不能把整个 prepare 都当作 PCIe 等待。下一轮只记录三类数值：复制事件等待、RAM 专家交换、驻留表更新；
同时把自适应缓存换入字节算进去。旧图黄色部分主要是当前窗口 `fetch_blobs`，不代表全部 PCIe 传输。

**优先减少反复搬的字节。** 主干仍按访问热度选择换入与换出，并限制交换数量。
不同层专家大小不同，限制“几个专家”不等于限制“多少字节”。若统计证实频繁换来换去，可以增加每窗口字节预算、
最短驻留时间或冷却期，按预期节省时间与搬运成本选择换入。只记录汇总字节与计数，不保存专家编号。
先确认有抖动再加机制，避免为了缓存命中率增加更大的后台搬运。

**再考虑重叠。** 部分驻留的默认 kernel 路径仍大体是：驻留专家计算 → 等 flag B → `fetch_blobs` → 搬入专家计算。
可以研究把已确定需要搬的专家提前在另一条 stream 复制，与驻留专家计算重叠；需要严格的 buffer 生命周期和 event 依赖，
且复制 kernel 会占 GPU 执行资源、竞争 RAM 带宽，未必更快。复杂度高于延后缓存换入，放后面。
不能在上一层尚未给出路由时假定已经知道下一层所有需要的专家。

**大页需要先适配当前分配路径。** 若考虑减少 CPU 地址翻译开销，必须研究把当前 cache complement 安全地迁移到可注册的大页内存；涉及 CUDA 注册、部分锁页、释放方式和 WSL 驱动兼容性，不能只打开 THP 开关就算完成。优先级低于工作线程与现有 AVX2 开关。

**独立测搬运内核的上限。** `src/kernels/cuda/verify_kernels.cu` 的 `fetch_blobs` 仍固定 384 blocks × 256 threads。
可以在相同固定总字节、相同 pinned 内存、不同批量大小下做小范围启动配置测试，再看端到端是否改善。
旧样本约 11.5 GB/s 是逻辑字节除以 kernel 时间，不能直接当作链路物理带宽，也不能保证改 kernel 就能翻倍。

**先不归咎 SSD。** 此前正式测量的热运行窗口 `file_mb=0`，没有证据说明这些窗口等的是 SSD。
优先处理 RAM/GPU 数据路径和调度；冷启动问题另算。

## Profiler 限制

上游 `Verifier::record_window` 在 `prof_on_` 时关闭共享专家的独立 stream。
我们的旧 timeline 会打开 `prof_on_`，因此它不能如实代表 0.1.39 默认并行调度。
此次增加明确保护：采集工具要求显式传入 `--legacy-serial`（设置 `STRATA_SH_STREAM=0`），否则在加载模型前退出；原生入口也检查此条件，新采集图明确标注串行诊断模式。
现有网页与 18 个窗口继续代表旧版本，不冒充新主干结果。此次速度回归关闭所有计时探针，并保持新默认共享专家重叠。
后续如需新版本 timeline，应给两条 GPU stream 各自打点，再按时间区间并集统计工作与等待。

### 同机短回归：旧生产引擎 0.1.36 → 合并版 0.1.39
